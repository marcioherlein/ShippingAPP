# ShippingAPP UI Audit — 2026-09-01

## Executive summary

ShippingAPP has a strong product-level foundation: the primary journey is explicit, the product explains why information is required, the calculation pipeline exposes blockers instead of inventing data, and the final quote includes cost traceability. The main UX risks are not cosmetic. They are state correctness, accessibility, and system consistency.

**Audit result: 29 Pass / 19 Fail across 48 criteria.**

### Highest-priority findings

1. **P1 — Editing operation inputs can leave a stale calculated state visible.** `App.tsx` allows the user to reopen Profile or Budget without invalidating `calculationStatus`, `pipelineSummary`, or the calculated result. `ImportQuoteFlow.tsx` initializes `purpose`, `entityType`, `hasImporterSignature`, `sensitiveCategory`, budget, quantity and product inputs with `useState(...)`, while the parent `key` does not include the operation fields. This creates a credible stale-result path after editing inputs that materially affect taxes/costs.
2. **P1 — Focus visibility is incomplete.** `base.css` removes the native input outline. Focus is restored only for `input`, not consistently for buttons, selects, textareas, summaries or links. `mobile-polish.css` explicitly removes focus outline on bottom navigation links.
3. **P1 — Dynamic calculation status is not announced to assistive technology.** The pipeline has strong visible statuses but lacks `aria-live`, `role="status"`, or a semantic progressbar. The visual progress element only has `aria-label`.
4. **P1 — Small secondary text fails WCAG AA contrast in common cases.** `#94a3b8` on white has a contrast ratio of approximately **2.56:1**, yet it is repeatedly used for 9–12 px labels and metadata. Normal text requires 4.5:1 under WCAG AA.
5. **P1 — Operation/budget validation is incomplete.** `budgetAnswered` only verifies that a mode was selected. There is no journey-level guard for zero budget, `unitsMin > unitsMax`, or invalid ranges before continuing.
6. **P2 — Selection controls are visually custom but semantically weak.** Chip buttons act like radio groups but do not use `fieldset/legend`, `role="radiogroup"`, or `aria-pressed`/radio semantics.
7. **P2 — Motion does not respect reduced-motion preferences.** The app uses global smooth scrolling, programmatic smooth scrolling, animated spinners and progress scans with no `prefers-reduced-motion` override.
8. **P2 — The visual system is fragmented.** The app imports a large stack of specialized CSS files, starts with Inter in `base.css`, then overrides the whole app with SAP `72` in `visual-consistency.css`, and retains multiple older mobile/desktop style systems. This raises the probability of style drift and override regressions.
9. **P2 — The conversational shell still behaves substantially like a form.** The bubbles explain the flow well, but most decisions are made in static cards/chips rather than through a consistent conversational input model.
10. **P2 — CI does not include automated accessibility or browser-level UX checks.** Current CI covers unit/integration, schema, build, runtime and production-shell smoke tests, but not axe, Lighthouse, Playwright keyboard paths, contrast regression, or reduced-motion checks.

- `.github/workflows/deploy-production.yml`

The production URL is configured as `https://shippingapp.marciofabrizio.workers.dev`. This environment could verify the deployment configuration but could not render that domain visually. Therefore visual-only details such as exact blur appearance, clipping under real browser font metrics, and screenshot-level spacing need a final browser pass. The Pass/Fail decisions below are based on implementation evidence and are intentionally strict.

## Priority remediation backlog

### P1 — Fix before additional visual polish

1. **Invalidate/recalculate downstream state when upstream operation inputs change**
   - Reset `calculationStatus`, `pipelineSummary`, `pipelineStage` and dependent quote state when purpose/entity/signature/sensitive category/budget inputs change after calculation.
   - Ensure `ImportQuoteFlow` synchronizes props or is keyed by every calculation-affecting setup field.
   - Add regression tests: calculate → edit purpose/signature/category/budget → verify displayed cost recomputes and stale summary disappears.

2. **Create one global focus-visible system**
   - Do not rely on browser-outline removal.
   - Add consistent `:focus-visible` treatment for `button`, `a`, `input`, `select`, `textarea`, `summary`, and any future custom controls.
   - Remove `outline:none` from bottom-navigation focus.

3. **Fix contrast tokens**
   - Replace light metadata colors used for functional text with AA-compliant tokens.
   - Treat 9–12 px text as normal text requiring at least 4.5:1.
   - Run automated axe/Lighthouse contrast checks.

4. **Make pipeline updates accessible**
   - Add `role="status"` / `aria-live="polite"` for loading/blocker/completion copy.
   - Convert overall progress to `role="progressbar"` with `aria-valuemin`, `aria-valuemax`, `aria-valuenow`.
   - Expose active step with `aria-current="step"` where appropriate.

5. **Validate operation and budget before advancing**
   - `budget > 0` for budget mode.
   - `unitsMin > 0`, `unitsMax > 0`, `unitsMin <= unitsMax` for unit mode.
   - Show inline error text connected with `aria-describedby` rather than silently disabling continue.

### P2 — Product-system cleanup

6. **Convert chip questions to semantic single-select groups** using fieldset/legend + radios, or buttons with explicit pressed/selected semantics.
7. **Add `prefers-reduced-motion` behavior** for smooth scroll, spinner, scan and hover transforms.
8. **Unify typography and design tokens** into one source of truth for font, spacing, radius, surfaces, text colors and states.
9. **Reduce style-layer fragmentation** by retiring legacy/overlapping mobile styles and consolidating journey components.
10. **Collapse completed context after calculation** so the result becomes the primary surface instead of appending indefinitely below the whole intake.
11. **Make the copilot interaction more coherent**: use a persistent composer or clearly decide that ShippingAPP is a guided wizard rather than visually implying full chat everywhere.
12. **Add automated accessibility/browser checks to CI**: Playwright keyboard flow + axe, reduced-motion test, viewport screenshots or visual regression.

### P3 — Polish

13. Replace Unicode glyphs with one icon library/system.
14. Increase small mobile target sizes toward Apple HIG 44 pt where practical.
15. Reduce false precision in estimated volume/cost displays.
16. Improve disabled-button explanations.
17. Consider an early “preview” for known products before collecting every planning input.

## Recommended implementation order

**Batch 1 — correctness:** stale-state invalidation + numeric validation + regression tests.

**Batch 2 — accessibility:** focus-visible + semantic groups + dynamic announcements + contrast + reduced motion.

**Batch 3 — design system:** tokens, typography, icons, style consolidation.

**Batch 4 — journey refinement:** collapse completed stages, reduce cognitive load, make conversational model consistent.

**Batch 5 — automated gates:** axe/Playwright/Lighthouse or equivalent CI checks.

## Definition of done

The UI audit should be considered remediated when:

- all P1 items are fixed and regression-tested;
- keyboard-only completion of the primary journey is possible with visible focus;
- screen readers receive meaningful loading/progress/error/completion updates;
- normal functional text meets WCAG 2.2 AA contrast;
- editing any cost-affecting upstream input cannot leave a stale result visible;
- 320–430 px mobile flows complete without horizontal page overflow;
- reduced-motion users do not receive forced smooth scrolling or continuous decorative motion;
- the application uses one typography/token/icon system;
- the result state clearly dominates the page once calculation is complete.
